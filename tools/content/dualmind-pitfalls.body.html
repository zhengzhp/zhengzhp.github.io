写在前面

上一篇写了 DualMind 的架构和选型，这篇只记踩过的坑。之所以单独成文，是因为下面这些问题里，有几个的「症状」和「根因」隔得特别远——远到如果不写下来，下次一定还会再踩一遍。

1. 页面真的没采到正文（分段器问题）；

同一轮排查还挖出两个相关的坑：

3. 语言选择器被会话态覆盖：工作台的语言下拉显示的是「上次实际使用的语言」（存在会话里），而不是持久化设置。于是会出现「下拉里显示中文、设置里其实存的是 en」的假象；用户再选一次「中文」不触发 onChange，设置就永远改不回去。修法是选择器只反映持久化设置。
4. 设置被整对象覆盖：设置页保存时提交的是完整的 settings 对象，而它是页面加载时的旧快照，会把其他入口刚写入的值覆盖回去。修法是新增 diffSettings()，只提交相对基线的增量字段，由 Background 做浅合并。

一个笼统的错误文案，代价是四个 bug 一起藏了很久。

坑 3：sidePanel.open() 的瞬时手势窗口

症状：点右键菜单「翻译整页」时，偶尔报 sidePanel.open() may only be called in response to a user gesture；更糟的是这个异常被外层 catch 捕获，用错误信息覆盖掉了刚刚写好的翻译结果。

根因：sidePanel.open() 必须在「瞬时用户激活（transient activation）」窗口内调用。网页里的点击激活能一路传到 Service Worker，但经不起 open() 之前多一次异步往返——等它返回时，激活已经过期了。

坑 4：模型把原文抄了回来，还报「翻译完成」

症状：用 qwen2.5-coder:7b 做整页翻译，界面显示「翻译完成」，但译文和原文一模一样。

坑 5：流式输出时，「停止」按钮偶发失灵

症状：翻译正在流式输出时点「停止」或「关闭」，有时候没反应。

根因：浏览器只有在 mousedown 和 mouseup 落在同一个节点上时才会派发 click。而浮层当时是「每来一个 chunk 就重建按钮节点」，用户按下的那一刻节点正好被换掉，click 就丢了。

修法有三条，缺一不可：

1. DOM 骨架只建一次，绝不重写 innerHTML，流式只更新文本节点；
2. 事件用委托只绑一次，不随节点重建而重绑；
3. 引入会话代际 sessionId：关闭或发起新请求时递增，让在途 chunk 和旧回调自动失效。

sessionId 顺带还解决了另一个问题：复制按钮的「已复制」提示，用旧定时器回调污染新会话——现在连点也不会提前复位。

还有两个小但很烦的细节：按钮要设固定 min-width，否则「复制 → 已复制」「侧边栏 → 收起侧栏」这类文案切换会让整行重排；以及 [hidden] 的 UA 样式 display:none 优先级低于作者样式，必须在自己的样式里显式写一遍 .dm-status[hidden]{display:none}。

坑 6：错误提示会变成「钉子户」

症状：一次翻译失败后，错误提示一直挂在界面上，甚至和「翻译中 3/12」同时出现，自相矛盾。

根因有两个，都在状态管理上：

1. UI 把提示存在组件本地 state 里，只在「本视图内的操作」清空。当新一轮翻译由其他入口发起（悬浮按钮 / 右键菜单 / 划词浮层），本视图收不到清空动作，旧提示就永久挂着。
2. 沉浸式控制器里，一批失败后 this.error = message 之后再没有清除逻辑，后续批次成功了也依然挂着。

修法是把「错误态」的权威来源收敛掉：ImmersiveControl 每次成功取到状态就 setError('')；工作台改为从会话读 setError(sess.error ?? '')，让翻译会话成为唯一事实来源。

「部分失败」的提示则改成按批次记账：用一个 failedIds: Set 记录失败的片段 id，成功批次会把对应 id 移除，再由 refreshFailure() 统一刷新文案。这样全部补译成功后提示会自动消失，而不是把「部分失败」永远挂着，也不是把失败伪装成成功。

坑 7：测试自己的坑——E2E 种子被产品迁移悄悄改写

症状：划词浮层的 E2E 用例集体挂掉，本地手动测却是好的。

根因：E2E 用 worker.evaluate 直接往 chrome.storage.local 写种子设置，为了模拟「选中后自动显示」，种子里写了 toolbarTrigger: 'auto'。但产品恰好有一个迁移：把旧的默认值 auto 收敛成 shortcut。更巧的是，种子没写 local:migrations，于是迁移认为「还没执行过」，把种子改掉了——用例自然永远等不到浮层。

修法：种子一并写入迁移标记，并且取值从 MIGRATION_IDS 派生，这样以后新增迁移不需要手工同步。

E2E 里还有几个和 MV3 强相关的点值得记一下：

1. MV3 扩展只能用 persistent context 加载，配 --load-extension；
2. 无头模式下必须指定 channel: 'chromium'——Playwright 默认用的 headless shell 不支持 --load-extension，扩展根本不会加载；
3. 真实的 Side Panel 用例在无头下必失败（无头不产生 SIDE_PANEL 上下文），所以这些用例标了 test.skip(!E2E_HEADED)，只有 E2E_HEADED=1 时才跑；
4. 扩展没在 manifest 里配 key 时，ID 每次都不一样，只能从 Service Worker 的 URL 里动态解析。

另外 Playwright 配置必须把 workers 设成 1：扩展的 storage 和 Service Worker 是跨用例共享的，并行跑会互相污染。

坑 8：开发期的两个「迷惑现象」

现象一：改了 content script，后台标签页没更新。
WXT 只对匹配到的标签页做热更新，而没被激活的后台标签仍跑着旧脚本。表现极具迷惑性：新功能「不生效」、浮层「关不掉」，但代码其实完全正确。排查前先确认「Reload 扩展 + 刷新页面」。

现象二：快捷键改了不生效。
Chrome 只在首次安装时采纳 suggested_key，Reload 和更新都不会重新绑定——这就是「快捷键有描述、按键却是空的」的常见原因。必须卸载重装，或在 chrome://extensions/shortcuts 手动设置。

还有一个开发体验上的坑：WXT 默认在 content script 变更时 reload 所有匹配的标签页，而这个项目的 matches 是 <all_urls>，体感像浏览器在无限刷页。最后在 Background 里 monkey-patch 了 tabs.reload，默认只刷当前活动标签。

小结：几条可复用的经验

1. 状态对象会「记住」你的错误：WeakSet 记得每一个元素，「已经打开的标记」记得每一次迁移，错误提示记得每一次失败。凡是「一次写入、长期有效」的状态，都要问一句「什么情况下它应该被清掉」。
2. 笼统的错误文案会放大排查成本：「没有正文」这一句话，藏了四个 bug。0 结果时一定要区分成因。
3. 不要假装成功：模型回显、部分片段失败，都应该显式标成「未翻译」，而不是拿原文或成功态糊过去。
4. MV3 的手势只有一瞬间：所有需要用户激活的 API，前面不能有 await。
5. 别重建正在被点击的节点：骨架只建一次 + 事件委托，是流式 UI 的基本功。
6. 测试数据要跟着产品规则走：迁移、默认值这类「隐形逻辑」最容易让测试在被改动后悄悄失效。
