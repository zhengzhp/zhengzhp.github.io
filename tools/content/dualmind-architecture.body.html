写在前面

DualMind 是我最近在做的一个 AI 浏览器助手（Chrome / Edge，Manifest V3），第一版只聚焦一件事：翻译。具体是网页划词翻译、Side Panel 工作台，以及整页沉浸式双语对照翻译。模型不经过我自己的服务器，而是走 BYOK——用户自己填 OpenAI 兼容端点（DeepSeek / Groq / 各类中转 / 自建 vLLM 都行），或者直接连本机的 Ollama。

这篇文章记录的是「架构」这一层：技术选型是怎么定的、目录为什么这么切、以及两条我认为最值得坚持的设计边界。踩过的坑另开一篇写。

一、技术选型：为什么是 WXT + React 19 + Tailwind

浏览器扩展的工程化过去几年一直有点「野生」。手写 Vite 当然能跑，但 MV3 有一堆绕不开的琐碎事：manifest 的多环境差异、content script 的注入与热更新、扩展页的独立入口、不同浏览器的产物差异。这些都不是业务逻辑，却极其吃时间。

最后选了 WXT（基于 Vite），理由是它的抽象层级刚好合适：

1. 文件式入口：entrypoints/ 下的文件路径本身就是入口声明，不需要手写一堆 build 配置；
2. 多浏览器：同一份代码 wxt build -b firefox 就能出 Firefox 产物；
3. 开发体验：content script 支持热更新，而且 createShadowRootUi 这种高频需求已经封装好了，少写不少样板代码。

框架层面是 React 19 + TypeScript + Tailwind。这里有个容易被误解的点：React 只用在扩展自己的页面（Side Panel、全页工作台、设置页），绝不注入宿主网页。宿主页面上只有划词浮层和沉浸式译文的 DOM 追加，用的是原生 DOM API。原因在后面「两条硬边界」里会展开。

三、两条硬边界

整个项目其实就靠两条规则撑着，后面所有的设计几乎都是它们的推论。

边界一：只有 Background 调模型，密钥不出内容脚本

Content Script 运行在别人的网页里，宿主页面理论上能通过 DOM 事件、原型链等方式去窥探同环境里的东西。所以 API Key 从设计上就不允许出现在 Content Script 中：Key 只存在 chrome.storage.local 的 settings 里，只有 Background 读得到，Provider 实例也只在 Background 创建。

边界二：Provider 层永不碰 DOM

providers/ 里只有「请求 → 文本流」这一件事，不 import 任何 DOM 相关的东西。这条边界带来两个实际收益：

1. Provider 可以在 Node 环境里被单测直接覆盖（不需要 jsdom），SSE 分包、错误码映射这类逻辑测起来非常轻；
2. 换模型服务时，改动范围被锁死在 providers/ 内，不会污染到页面上「怎么渲染译文」的逻辑。

四、消息协议：自研的类型化 messaging

扩展开发里最容易失控的地方之一，就是「消息满天飞」。今天 {type:'translate'}，明天 {action:'doTranslate'}，最后没人说得清总共有多少种消息。所以我用一张 ProtocolMap 把消息名和它的入参/返回值类型绑死：

客户端封装统一把响应拆成 {ok:true,data} / {ok:false,error,code}，调用方不用每次自己判空：

更关键的是长连接 Port。流式翻译和沉浸式批量翻译都走 Port，而不是反复 sendMessage，原因有三个：

1. 一次建连多次回传：chunk 直接推给 UI，不用为每个 token 起一次消息往返；
2. 天然支持 abort：断开 Port 就是取消，配合 AbortSignal 能干净地停掉底层 fetch；
3. 可以并发多批：沉浸式翻译给每个批次分配独立 requestId，在同一条 Port 上用 Map<requestId, pending> 管多路请求，各自独立取消。

项目里一共三条 Port：dualmind-translate（单段流式）、dualmind-immersive（整页批量、可并发）、dualmind-sidepanel（侧栏生命周期）。

于是「OpenAI 兼容」和「本地 Ollama」的差异被压缩到只剩一些配置项：base URL、鉴权头、模型列表端点。Ollama 的对话端点 /v1/chat/completions 本身也是 OpenAI 协议，所以两者复用同一个 SSE 解析器，调用链只差一个 base URL。

SSE 解析是手写的，没用 EventSource——因为它在扩展的 Service Worker 里不可用。用 fetch + ReadableStream + TextDecoder 增量解码，并且必须自己维护「半行缓冲」，否则 TCP 分包会把一行 JSON 劈成两半：

错误也统一收口：HTTP 状态映射成固定的 ErrorCode（401/403 → UNAUTHORIZED、404 → MODEL_NOT_FOUND、429 → RATE_LIMIT、408/504 → TIMEOUT），再由 shared/errors.ts 翻译成给用户看的中文文案。UI 层因此完全不需要关心「是哪个服务商报的错」。

六、MV3 权限取舍：<all_urls> 为什么删不掉

上架时最容易被质疑的就是权限。这个项目最终只保留了三个 API 权限——storage、sidePanel、contextMenus，但 <all_urls> 必须保留，而且它需要同时出现在两个地方，缺一不可：

位置作用去掉会怎样
content_scripts.matches划词浮层常驻注入，支撑「选中即自动显示」只能改 activeTab 按需注入，每页首次使用都要用户手势唤起，功能退化
host_permissionsBYOK 要请求用户自填的任意 Base URL，Service Worker 跨域 fetch 必需直接 Failed to fetch

那 optional_host_permissions 呢？看起来更「礼貌」，但收益其实为零：因为 content_scripts.matches 仍然是 <all_urls>，安装时的警告文案不会变，只是白白多了一个「运行时会失败」的入口。所以没用。

另外两个权限是主动砍掉的：activeTab 和 scripting。tabs.sendMessage 只要目标页已经有 content script 就能用，不需要 host 权限或 activeTab；项目也确实没调用 scripting.executeScript。保留一个用不到的权限，除了让审核问更多问题之外没有任何价值。

代价也要说清楚：安装时会出现「读取并更改您在所有网站上的数据」。这基本是划词类扩展的品类固有成本——你要在任意页面上响应选中，就必然要在任意页面上注入。能做的只是把「为什么要」写清楚，而不是假装不需要。

七、小结

回头看，这个项目里最有价值的其实不是某个具体实现，而是那两条边界：密钥不出内容脚本、Provider 不碰 DOM。它们不是性能优化，也不会让某个功能变得更快，但它们决定了这个代码库在加了 Chat、Agent 之后还能不能保持可读。

架构的价值往往不在「能做什么」，而在「不允许做什么」。
